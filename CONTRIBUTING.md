# Contributing to Vix

**Welcome!** We're excited you're interested in contributing to Vix. This guide
will help you get started, whether you're fixing a bug, adding a feature, or
improving documentation.

Vix is a **keyboard-friendly terminal IDE** built on `ratatui`, with 147 focused
crates, 14 keymaps, LSP/DAP, Git, a database workbench, Org mode, and more.

---

## Quick Start

### Prerequisites

- **Rust**: 1.97 or newer (current stable minus two)
- **Git**: For version control
- **A terminal**: Vix is a terminal application

### Setup

```sh
# Clone the repository
git clone https://github.com/vixide/vix.git
cd vix

# Build and run
cargo run
```

That's it! Vix will open in your terminal.

## Contribution Workflow

### 1. Find Something to Work On

#### For Beginners

- Look for issues labeled **[`good first issue`](https://github.com/vixide/vix/labels/good%20first%20issue)**
- Check the **[`help wanted`](https://github.com/vixide/vix/labels/help%20wanted)** label
- See our [roadmap](#roadmap) below

#### For Experienced Contributors

- Browse **[open issues](https://github.com/vixide/vix/issues)**
- Check **[plan.md](plan.md)** for major initiatives
- See **[tasks.md](tasks.md)** for detailed task list

### 2. Create a Branch

```sh
# Create a feature branch from main
git checkout -b feat/your-feature-name
```

**Branch naming conventions:**
- `feat/...` - New features
- `fix/...` - Bug fixes
- `docs/...` - Documentation changes
- `refactor/...` - Code refactoring
- `test/...` - Test additions
- `chore/...` - Maintenance tasks

### 3. Make Your Changes

Follow the [development guidelines](#development-guidelines) below.

### 4. Test Your Changes

```sh
# Run the full check gate
./scripts/check

# Or for faster iteration
./scripts/check --tier fast  # fmt, clippy, tests of changed crates
./scripts/check --tier push  # full workspace + docs
```

### 5. Commit Your Changes

```sh
# Stage your changes
git add .

# Commit with a descriptive message
git commit -m "feat: add your feature description

Detailed description of changes.

Generated by Mistral Vibe.
Co-Authored-By: Mistral Vibe <vibe@mistral.ai>"
```

**Commit message guidelines:**
- Use **imperative mood**: "Add feature" not "Added feature"
- **First line**: 50-72 characters, summary of changes
- **Body**: Explain what and why (optional for small changes)
- **Footer**: AI co-authorship trailer if applicable

### 6. Attest and Push

```sh
# Run the full gate and create signed attestation
./scripts/attest

# Push your branch
git push origin feat/your-feature-name
```

The `pre-push` hook (installed via `make hooks`) will verify you have a valid
attestation before pushing to `main` or tags.

### 7. Create a Pull Request

1. Go to **[GitHub Pull Requests](https://github.com/vixide/vix/pulls)**
2. Click **"New Pull Request"**
3. Select your branch
4. Fill in the PR template
5. Wait for CI to pass
6. Address any feedback from reviewers

## Development Guidelines

### Code Standards

#### Rust Conventions

- **Edition**: 2024
- **Linting**: `clippy::pedantic` with `-D warnings` (zero warnings allowed)
- **Formatting**: `cargo fmt` (rustfmt)
- **Documentation**: Every public item must have `///` doc comments
- **Safety**: **Zero `unsafe`** - enforced by `[workspace.lints.rust]`

#### Every `#[allow()]` Must Have a Reason

```rust
// Good
#[allow(clippy::too_many_lines, reason = "This function handles many related cases")]

// Bad (will fail CI)
#[allow(clippy::too_many_lines)]
```

### Architecture

Vix is organized as a **Cargo workspace** with:

```
vix/
├── Cargo.toml           # Root workspace
├── tui/                 # Main app shell (vix-tui package)
│   └── src/             # Application code
├── crates/              # 147 feature crates (vix-*)
│   ├── vix-editor/      # Editor core
│   ├── vix-lsp/         # LSP client
│   ├── vix-git/         # Git integration
│   └── ...              # Many more
├── gui/                 # Desktop GUI front ends
└── spec/                # Cross-cutting specifications
```

**Key principles:**
- **One crate per feature** with clear boundaries
- **Specs are source of truth** - each crate has `spec/index.md`
- **Zero `unsafe`** code anywhere in the workspace
- **Every user-facing string** uses `t!()` for internationalization

### Internationalization (i18n)

All user-facing text must be internationalized:

```rust
// In your code
use crate::t;

fn show_message() {
    println!("{}", t!("my_feature.welcome_message"));
}
```

```yaml
# In crates/vix-i18n/locales/en.yml
my_feature:
  welcome_message: "Welcome to Vix!"

# In crates/vix-i18n/locales/es.yml
my_feature:
  welcome_message: "¡Bienvenido a Vix!"
```

**15 languages supported**: en, es, fr, de, cy, ga, gd, pl, pt, ru, ar, hi, bn, zh, ja

### Testing

Vix has several testing layers:

| Layer | Purpose | Location |
|-------|---------|----------|
| Unit Tests | Test individual functions | In each crate (`src/*.rs`) |
| Integration Tests | Test feature interactions | `tui/tests/integration/` |
| Snapshot Tests | Test UI rendering | `tui/tests/snapshots.rs` |
| Fuzz Tests | Test parser edge cases | `fuzz/fuzz_targets/` |
| Benchmarks | Test performance | `tui/benches/` |

**Run tests:**
```sh
cargo test --workspace           # All unit + integration tests
cargo test --workspace --doc    # Include doc tests
./scripts/check                  # Full gate including tests
```

### Documentation

#### Code Documentation

Every public item must have doc comments:

```rust
/// Opens a file at the given path.
///
/// # Arguments
/// * `path` - The path to the file to open
///
/// # Returns
/// `Result<(), FileError>` - Ok if successful, Err otherwise
pub fn open_file(path: &Path) -> Result<(), FileError> {
    // ...
}
```

**Build docs:**
```sh
cargo doc --workspace --no-deps --open
```

#### User Documentation

User docs live in `docs/`:n
- `docs/getting-started/` - Getting started guides
- `docs/reference/` - Reference documentation
- `docs/compare/` - Comparison with other editors
- `docs/tutorials/` - Tutorials (needs expansion)

**Docs must:**
- Use consistent terminology
- Include examples where helpful
- Link to related documentation
- Be kept up-to-date with code changes

## Feature Development

### Adding a New Feature

1. **Read the spec** - Find or create `crates/vix-*/spec/index.md`
2. **Add action id** - Register in palette and menu
3. **Add i18n strings** - Add to all 15 locale files
4. **Implement** - Write the code
5. **Add tests** - Unit and/or integration tests
6. **Add documentation** - User-facing docs
7. **Update CHANGELOG** - Record user-visible changes

### Example: Adding a Simple Command

```rust
// In tui/src/app.rs - add to run_action match
"my_feature.do_something" => {
    self.do_something();
    Ok(())
}

// In crates/vix-menu/src/lib.rs - add to menu
MenuItem::new(
    "my_feature.do_something",
    t!("menu.item.my_feature.do_something"),
    Some(t!("menu.item.my_feature.do_something.help")),
)

// In crates/vix-i18n/locales/en.yml - add strings
menu:
  item:
    my_feature:
      do_something: "Do Something"
      do_something.help: "Perform a useful action"
```

### Adding a New Crate

1. Create directory: `crates/vix-new-feature/`
2. Add `Cargo.toml` with `[lints] workspace = true`
3. Add `spec/index.md` explaining the feature
4. Add to root `Cargo.toml` under `[workspace.dependencies]`
5. Register in `agents/share/crate-map.md`

## Spec-Driven Development

Vix uses a **spec-first** approach:

1. **Spec** - Define behavior in `spec/index.md`
2. **Implement** - Write code to match spec
3. **Test** - Verify code matches spec
4. **Document** - Explain feature to users

**Spec format:**
- Start with the **contract** (what it does)
- Use **tables** for enumerable things
- Explain **why** for non-obvious decisions
- Name the **code** that implements it
- Link to **related specs**

**Keep specs and code in sync:**
```sh
scripts/check-docs  # Validates spec links and coverage
```

## FAQ

### How do I build Vix?

```sh
git clone https://github.com/vixide/vix.git
cd vix
cargo build --release
```

The binary will be at `target/release/vix`.

### How do I run tests?

```sh
cargo test --workspace
```

For faster iteration:
```sh
./scripts/check --tier fast
```

### How do I add a new feature?

1. Find or create the spec
2. Add the action id to `run_action`
3. Add menu item and palette command
4. Add i18n strings
5. Implement the feature
6. Add tests
7. Update documentation

### How do I add a new language?

1. Copy `crates/vix-i18n/locales/en.yml` to `crates/vix-i18n/locales/xx.yml`
2. Translate all strings
3. Add to `crates/vix-locale-model/src/lib.rs`
4. Test with `cargo run -- --locale xx`

### How do I contribute a theme?

1. Create a JSON file in `~/.config/vix/themes/`
2. Follow the format in existing themes
3. Share your theme with the community!

### How do I write a Rhai script?

See the [scripting documentation](docs/scripting/index.md) for the full API.
