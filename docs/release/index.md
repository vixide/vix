# Releasing Vix

A release goes out by pushing a version tag: the tag starts
`.github/workflows/release.yml` (generated by `dist`), which builds every
target and publishes every channel. 2.0.1 and 2.0.2 shipped this way.
`scripts/release-local` is the local alternative; it was used for real once,
for 2.0.0, which therefore shipped only three archives. **Cutting a tag or a
GitHub Release is always the maintainer's decision** ([`AI_STATEMENT.md`](../../AI_STATEMENT.md));
`cargo publish` is pre-authorized under its §1–§5 checklist.

## The normal path: a tag on `main`

1. Cut the changelog: `CHANGELOG.md` needs a `## [2.0.2]` section (not just
   `[Unreleased]`) and the workspace version must match.
2. Run the whole gate on the commit to release (`scripts/check`, or
   `scripts/attest`, see [Contributing](../contributing-workflow.md)), push it
   to `main`, and wait for CI to be green.
3. **Tag only a commit that is already on `main` on GitHub.** `dist`'s `host`
   job creates the GitHub Release with the tagged commit as its target, and
   `GITHUB_TOKEN` gets `HTTP 403: Resource not accessible by integration` for a
   commit that is on no branch (see [`spec/ci`](../../spec/ci/index.md)). With
   the maintainer's say-so, push a signed tag such as `2.0.2`.
4. Watch the release run (`gh run watch`). It builds the archives (including a
   static musl build, whose flags come from `.github/dist/build-setup.yml`),
   the shell and PowerShell installers, the MSIs and the GUI archives, creates
   the GitHub Release, pushes the formulas to the `vixide/homebrew-tap`
   Homebrew tap and publishes `@vixide/vix` to npm; the `linux-packages`
   workflow then builds and tests the `.deb`, `.rpm` and Arch packages. A
   failed publish job can be re-run on its own once its cause is fixed.
5. Publish the crates: `cargo publish` for every workspace crate, in
   dependency order, after the checklist in `AI_STATEMENT.md` §1–§5.
   crates.io rate-limits new versions (about 30 crates at once, then about one
   a minute), so publishing all of them takes a couple of hours. The run is
   resumable: skip every crate already at the version and carry on.

## The local alternative: `scripts/release-local`

`scripts/release-local` (T766) builds the three Makefile release targets,
checksums them, signs the checksums with the maintainer's SSH key, and can
upload them to GitHub and Codeberg. It never creates or pushes a tag unless
given the separate `--tag` flag.

1. Rehearse: `scripts/release-local 2.0.2 --dry-run`. This checks the
   preconditions, runs `make build-macos build-windows build-linux`, writes
   `target/release-local/2.0.2/`, signs it, and prints the exact `gh` and `tea`
   commands an upload would run. It uploads nothing and tags nothing. The default
   (no flags) behaves the same.
2. Check the result as a downloader would:
   `scripts/release-local --verify-dir target/release-local/2.0.2`.
3. Decide about the tag. `scripts/release-local 2.0.2 --tag` makes a signed
   annotated tag locally and nothing else. Pushing it is the maintainer's
   decision, and pushing it also starts `release.yml`, which builds and creates
   the full release, so decide which path is the release before you push.
4. Upload: `scripts/release-local 2.0.2 --publish`. It refuses unless the tag
   already exists on both forges, asks you to type
   `publish 2.0.2 to github codeberg` exactly, then runs `gh release create
   --verify-tag` (or `gh release upload --clobber` when the release exists) and
   `tea releases create`.

### What it refuses

A tree that is not clean, a branch other than `main`, a `HEAD` tree without a
valid full-tier attestation (`scripts/attest --verify`), a version that is not
the workspace version or has no changelog section, a missing build tool or cross
linker, and (for `--publish`) a missing tag or a confirmation that does not match.

### Assets

For each target the script writes `vix-tui-<target>.tar.xz` (`.zip` for Windows),
a matching `.sha256`, one `SHA256SUMS`, and `SHA256SUMS.sig`
(`ssh-keygen -Y sign -n vix-release`, verified with the allowed signers file that
signs commits). A downloader verifies with `scripts/release-local --verify-dir DIR`
or `ssh-keygen -Y verify -n vix-release`.

## Packaging handoff

`scripts/packaging render 2.0.2 --sums SHA256SUMS` reads a release's
checksums to fill the winget, Scoop and AUR templates; nothing is published.
The templates name the `dist` targets (`*-pc-windows-msvc`,
`*-unknown-linux-gnu`), so render them from a `dist` release's checksums; the
local release builds `x86_64-pc-windows-gnu` and `x86_64-unknown-linux-musl`,
and `render` reports the assets it lacks.

See [`spec/ci`](../../spec/ci/index.md) and
[`spec/local-ci`](../../spec/local-ci/index.md) for the design.
